# Offer Hunter 隐私政策

> 适用版本：1.0.4 ｜ 生效日期：2026-09-29 ｜ 最后更新：2026-09-29
>
> 本政策描述 Offer Hunter 浏览器扩展**当前实际的行为**，不是范本条文。
> 每条结论都在附录 A 里对应到源码位置，你可以自己核对。

## 摘要

- **我们没有服务器。** Offer Hunter 没有后端，也不接收、存储、查看你的任何数据。你的简历、API Key、分析结果只存在于你自己的浏览器里。
- **对外请求只有三个去处**：① 招聘网站自己的接口（只读取你正在看的那一个岗位）；② 你自己配置的 AI 端点（只在你点击分析或生成时）；③ 你选用 Gist 作为简历来源时的 GitHub。
- **没有任何统计、遥测、崩溃上报、广告或远程配置**，也不存在"匿名上报使用情况"这类东西。
- **API Key 与 Gist token 以明文存在本机**，浏览器扩展存储不做加密。
- **你可以随时清空全部数据**，卸载扩展同样会删除。

## 1. 我们是谁

Offer Hunter（下称"本扩展"）是一个开源的浏览器扩展，用于在已支持的招聘网站职位页上，用你自己配置的 AI 平台比对简历与岗位 JD 的匹配度，并生成一条招呼语。

| 项目 | 内容 |
| --- | --- |
| 运营者 | imba97（个人开发者） |
| 联系方式 | mail@imba97.cn |
| 项目主页 / 问题反馈 | <https://github.com/imba97/offer-hunter> ｜ <https://github.com/imba97/offer-hunter/issues> |
| 许可 | MIT（源码公开，可自行审计与构建） |

**适用范围**：本政策适用于 Offer Hunter 扩展本体，包括侧边栏、设置页、后台服务、内容脚本与注入脚本。

**不适用范围**：

- 你自行修改、构建或第三方重新打包的版本 —— 其数据处理方式以该版本的代码为准。
- 你配置的 AI 平台、你使用的招聘网站、GitHub 自身的隐私实践 —— 它们是独立的服务提供者，适用各自的隐私政策。

## 2. 我们处理哪些数据

### 2.1 你主动提供的数据

| 数据 | 说明 | 是否必须 |
| --- | --- | --- |
| 简历全文（Markdown） | 你手动粘贴，或从你指定的 Gist 同步而来。会随 JD 一并发往 AI 端点 | 使用分析功能时必须 |
| AI 平台配置 | 平台、接口地址、模型名、最大输出 Token、**API Key** | 必须 |
| 提示词 | 自定义打分口径与招呼语规则，默认留空 | 可选 |
| 简历来源配置 | Gist 链接或 ID、文件名、可选的 GitHub Personal Access Token | 选用 Gist 来源时 |

### 2.2 从招聘网站读取的数据

**只读取你当前打开的那一个岗位页**，且只在页面属于已支持的招聘网站时（当前为 `zhipin.com`、`eleduck.com`、`v2ex.com` / `v2ex.co`、`mediastorm.jobs.feishu.cn`，与 manifest 的 `host_permissions` 一致）。

读取内容因站点而异：

- **职位信息**：职位名、公司名、所属行业、公司规模、融资阶段、薪资、经验要求、学历要求、工作地点、技能标签。
- **招聘者信息**：招聘者姓名与职位（仅用于让招呼语的称呼更自然）。
- **JD 正文**：岗位描述全文。
- **站点内部标识**：招聘网站自己的岗位标识（如 BOSS 的 `securityId`、电鸭的帖子 slug、V2EX 的帖子 id、影视飓风岗位页地址上的那串数字）。**这些标识不会发送给 AI。**
- **接口原始响应**：有接口可取的站点（当前为 BOSS 与影视飓风）返回的原始 JSON，仅用于界面展示与故障诊断，**不写入本地存储**。

### 2.3 本地生成的数据

- 匹配结果：0–100 分、一句话结论、命中要点、缺失技能。
- 招呼语文本及其生成理由。
- 岗位账本：每个看过的岗位一条记录（见 3.2）。
- 诊断信息：接口捕获记录、页面选择器命中情况，仅在界面与内存中，不写入存储。

### 2.4 我们不收集的数据

明确地、逐项地：

- **不收集任何账号体系信息**：没有注册、没有登录、没有用户 ID、没有设备指纹、没有安装 ID。
- **不收集身份信息**：姓名、手机号、邮箱、身份证等 —— 除非你自己把它们写进了简历，那部分内容会随简历一起发给你选择的 AI 平台。
- **不读取 Cookie**：代码中不存在任何读取 Cookie 的语句，也未申请 `cookies` / `webRequest` 权限。需要说明的是：有接口可取的站点（当前为 BOSS 与影视飓风），其岗位详情请求由页面上下文发出，浏览器会按常规为该请求附上你在该站点的登录 Cookie；扩展本身既不读取、也不存储 Cookie 内容。
- **不读取其他网站**：主机权限只覆盖已支持的招聘网站域名，即 `zhipin.com`、`eleduck.com`、`v2ex.com` / `v2ex.co` 与 `mediastorm.jobs.feishu.cn`（见第 5 节）。
- **不收集浏览历史、书签、下载、位置、通讯录、日历、付款信息**。
- **不做统计与遥测**：代码中不存在任何分析、埋点、崩溃上报或远程配置代码（附录 A 第 12 项）。
- **不含广告，不投放广告，不参与广告画像。**
- **不向任何第三方出售、出租或交换你的数据。**

## 3. 数据存储在哪里、存多久

### 3.1 存储位置

全部数据存放在**扩展自己的 IndexedDB 数据库**（库名 `offer-hunter`）里，分三个对象仓库：

| 仓库 | 内容 |
| --- | --- |
| `settings` → `resume` | 简历全文、简历来源配置（含可选 Gist token）、同步时间 |
| `settings` → `ai` | AI 平台、接口地址、模型、最大 Token、**API Key** |
| `settings` → `prompts` | 你的自定义提示词（打分口径、招呼语规则） |
| `records` | 岗位账本（每个岗位一条，键是 `站点:岗位标识`） |
| `meta` | 迁移与自检记录（不含任何个人内容） |

除此之外**没有任何其他落盘位置**：不使用 `storage.sync`、不使用 `storage.session`、不使用 localStorage / Cache API / Cookie，也不写文件系统。

（1.0.4 及更早的版本把同样的数据放在 `chrome.storage.local` 的四个键里；升级到 1.1.0 时它们会被迁移进上面的数据库，**校验无损之后旧键即被删除**，不留副本。）

**关键事实：**

- **明文存储。** 浏览器扩展存储不做加密，我们也没有额外加密。能读取本机浏览器配置目录的人（包括同一台电脑的其他使用者、能访问你磁盘的软件）就能读到其中的 API Key 与简历。**建议使用设置了额度上限的 API Key。**
- **不随浏览器账号同步。** 数据只在本机磁盘（IndexedDB 不参与浏览器账号同步），不跨设备同步。
- **网站读不到。** 扩展存储与网页隔离，包括上述招聘网站本身。
- **会请求浏览器持久化存储。** 首次初始化时会调用 `navigator.storage.persist()`，请浏览器不要把这份数据当作可回收的缓存清掉；这是尽力而为的请求，失败也不影响使用。

### 3.2 岗位账本的内容与上限

账本每条记录的字段：站点、岗位标识、职位名、公司名、招聘者姓名、薪资、匹配结果（分数 / 结论 / 命中点 / 缺失技能）、招呼语、错误信息、首次记录时间。

**账本不保存 JD 原文。** 需要注意的是两点边界情况：

- 错误信息里可能包含最多 200 字的模型返回片段，或你配置的接口地址（例如超时报错会带上 URL）。
- 当招聘网站没给出稳定岗位标识时，账本改用本地按岗位内容算出的摘要（不可逆哈希，不是原文）作为键。
- **历史说明**：1.0.4 及更早的版本曾在账本里保存过 JD 原文与部分页面字段。1.1.0 迁移时会把这些记录归一成当前形状并**清除这些字段**（迁移前可在设置页自行导出备份）。因此上面这句话在升级之后对所有记录都成立。

**数量上限：2000 条，滚动更新。** 超过之后，每写入一条新记录就自动丢弃最旧的一条（按首次记录时间，写入时在同一个事务里执行，走 `firstSeen` 索引游标）。不做归档、不做上传、也不会弹出提示。这一条**始终生效**，与下面的保留期限互相独立。

### 3.3 保留期限

**默认没有过期时间**（设置页「岗位账本保留 → 按首次记录时间清理」默认为「永不清理」），数据一直保留到你主动删除为止。

你可以把它改成「保留最近 30 / 90 / 365 天」。一旦设置，扩展会在启动时清理一次，并在你改动的当下立刻清理：

- 判据是**首次看到该岗位的时间**（`firstSeen`），不是最近一次使用的时间。因此一个很久以前记录、但你最近仍会回来查看的岗位也可能被清掉。
- 清理是本地删除，不可恢复（没有回收站、没有归档）。
- 无论这里选什么，上面的 2000 条上限都照常生效。

### 3.4 如何删除

设置页 →「清空本地数据」（含二次确认）。它会删除上述各仓库的全部内容：简历、Gist 配置与 token、API Key 与平台配置、提示词、整个岗位账本。

删除时的几个真实行为，提前说明：

- 删除后在库的就是**默认空值**（账本为空表），因此"库还在"但内容已清空。
- **所有已打开的页面会立即重置为默认值**（清空动作会广播到各上下文），不需要手动刷新。
- 系统剪贴板里已复制的招呼语不会被清掉。
- 招聘网站自身的登录状态（Cookie）不受影响 —— 那本来就由你的浏览器管理，扩展碰不到。
- 卸载扩展，浏览器会一并删除这些数据。

**我们没有你的数据副本**，因此无法（也不需要）代你导出或删除。你自己就是数据控制者。

## 4. 数据什么时候离开你的设备

这是本政策最需要读清楚的一节。除下表所列情形外，**不发往任何地方**。

| 接收方 | 触发时机 | 实际发送的内容 |
| --- | --- | --- |
| **你配置的 AI 端点**（DeepSeek / OpenAI / Anthropic / Kimi / 自定义） | 仅当你点击「分析匹配度」或「生成打招呼语」 | 系统提示词（内置要求 + 你的自定义提示词）、**你的简历全文**、岗位字段（职位/公司/行业/规模/薪资/经验/学历/地点/技能标签；生成招呼语时另含招聘者姓名与职位）、**JD 正文**、生成招呼语时另含本次匹配结论。超出模型输入上限时按平台上限截断（简历与 JD 都会被截，界面会提示"已截断"） |
| **你配置的 AI 端点**（连通性测试） | 仅当你点击「测试连通性」 | 只有一句 `回复 ok`。**不发送简历，也不发送 JD** |
| **GitHub**（`api.github.com`） | 选用 Gist 简历来源时：打开设置页会触发一次自动同步（同一份内容 10 分钟内不重复请求），或你手动点「同步简历」 | `GET /gists/<你的 Gist ID>`；固定请求头；若你填了 token，则以 `Authorization: Bearer` 发送该 token。**不发送简历内容、不发送岗位信息** |
| **招聘网站自身**（`zhipin.com` / `eleduck.com` / `v2ex.com`、`v2ex.co` / `mediastorm.jobs.feishu.cn`） | 打开侧边栏、切换/加载职位页、10 秒轮询兜底，或你点击刷新/诊断 | 扩展只读取页面与其接口响应；有接口可取的站点的岗位详情接口请求由页面上下文发出，浏览器会自动附上你**在该站点的登录 Cookie**（扩展本身不读取 Cookie 内容）。扩展不向这些站点上传任何额外数据 |

补充说明：

- **请求中不含任何身份标识。** 发往 AI 端点的请求体里只有提示词与内容，没有用户 ID、安装 ID、设备指纹、邮箱或版本号；唯一"标识"是你自己的 API Key（放在请求头里，不放在 URL 里）。由于是普通跨域请求，请求会带上扩展自身的 `Origin` 头。
- **不会自动调用 AI。** 分析、生成、连通性测试都只由你的点击触发；没有安装即上报、没有"打开页面就偷偷分析"，也没有任何定时上报。
- **不依赖点击的联网只有两处**，都不涉及 AI：① 你在已支持的职位页打开侧边栏（或切换标签页、页面加载完成）时，内容脚本会去读取该岗位信息 —— 数据本来就是这个页面要展示给你的；② 已配置 Gist 简历来源时，打开设置页会同步一次简历（同一份内容 10 分钟内只请求一次）。
- **本地模型完全不出本机。** 选择"自定义端点"并填写 `http://localhost:11434/v1`（Ollama）或 LM Studio 等本地地址时，简历与 JD 都不会离开你的电脑 —— 这是唯一一种内容全程不由第三方经手的配置。
- **超时与取消。** AI 请求 90 秒超时、连通性测试与 Gist 请求 20 秒超时；**没有自动重试**（失败就是失败，由你决定是否再点一次），也没有"手动取消"按钮。

## 5. 权限与页面访问

### 5.1 申请的权限，以及各自的用途

| 权限 | 用途 | 说明 |
| --- | --- | --- |
| `storage` | **仅用于读取旧版本遗留的 `chrome.storage.local` 数据，以完成一次性迁移**；日常读写走扩展自己的 IndexedDB（不需要任何权限） | 迁移校验无损后即删除旧键；不影响任何联网行为 |
| `sidePanel` | 用浏览器原生侧边栏承载全部界面 | 界面不注入页面，不遮挡、不打扰 |
| `tabs` | 判断当前标签页是不是已支持的招聘网站职位页，以及定位需要通信的那个标签页 | 该权限在技术上允许读取所有标签页的 URL/标题；代码中只查询"当前窗口的活动标签页"，不遍历、不记录、不上传其他标签页地址 |
| `activeTab` | **当前版本代码中没有任何一处依赖它** —— 站点判断完全由 `tabs` 与主机权限完成 | 如实说明：这属于一份可以收窄的多余权限面，我们计划在下个版本评估移除 |
| 主机权限 `*://*.zhipin.com/*`、`*://*.eleduck.com/*`、`*://*.v2ex.com/*`、`*://*.v2ex.co/*`、`*://mediastorm.jobs.feishu.cn/*` | 只在这几个站点的页面上读取你正在看的岗位 | 不是"所有网站"，读不到你访问的其他任何站点。影视飓风的招聘页跑在飞书招聘上，但这里**只申请它自己那一个租户子域**，不是整个 `*.jobs.feishu.cn`（那会覆盖该平台上所有公司的招聘页） |

### 5.2 页面里的脚本做了三件事

1. **隔离世界内容脚本**（所有已支持站点都有）：读取当前职位页的岗位信息，与侧边栏通信。
2. **MAIN 世界注入脚本**（只注入给有接口可取的站点，当前为 BOSS 与影视飓风）：为了被动拿到招聘网站自己的岗位接口响应，它在页面自身的 JS 环境里包装了 `window.fetch` 与 `XMLHttpRequest`，**只对已声明的接口路径做响应克隆解析**，其余请求连解析都不做，也不产生任何新请求。捕获到的岗位数据通过 `window.postMessage` 回传给扩展。
3. **DOM 兜底读取**：接口取不到时，从页面结构里读职位名与 JD 正文。

关于第 2 点的边界，如实说明：注入脚本与页面同源通信，因此**页面自身的脚本在理论上也能读到这条消息**；但消息内容全部来自该页面本来就会收到的岗位数据，**永远不包含你的简历、AI 结果或 API Key**。

同一条通道也是反向的：页面脚本理论上可以伪造消息，让面板把某个岗位当成"你正在看的那个"。这不会导致任何数据外泄（该通道只能把岗位数据递进来，递不出去你的简历或密钥），但确实意味着"当前岗位"这一显示内容由页面可控。若你发现面板显示的岗位与页面不符，点一次刷新即可。

### 5.3 明确不做的事

- 不读取 Cookie（未申请 `cookies` / `webRequest` 权限），不读取页面的 localStorage / sessionStorage。
- 不读取你访问的其他任何网站。
- 不向页面注入任何 UI，不修改页面外观（扩展未声明 `web_accessible_resources`，没有暴露给页面的资源）。
- **不在页面上执行操作**：不点击页面上的任何元素、不代填表单、不读取验证码，也不在页面上提交任何内容。
- 不逆向签名、不绕过平台频率限制。
- **不批量采集**：没有爬虫、没有队列、不在后台抓职位列表，只读取你当前打开的那一个岗位。
- 不加载任何远程代码：发布版扩展页的 CSP 为 `script-src 'self'`，没有 CDN 脚本、远程字体或图标请求（图标在构建时打包进产物）。

## 6. 第三方如何处理你的数据

我们把数据交给你选择的服务提供者之后，**其后续处理由它们各自的政策决定，我们无法控制也无法撤销**：

- **AI 平台**接收你的简历与 JD，可能按其条款保留日志、用于模型改进或人工审阅。各平台差异很大：请自行阅读其隐私政策与服务条款，优先选择明确承诺"不用于训练"的 API 条款，或直接使用本地模型。
- **GitHub**：使用 Gist 来源时，简历内容由 GitHub 存储与提供。
- **招聘网站**：你浏览职位页的行为受其自身隐私政策约束。

### 6.1 关于 secret Gist 的重要提醒

**secret Gist 不等于私有。** 它只是不被列出、搜不到，**拿到链接的人都能读**，不需要登录、也不需要 token。因此：

- 不要把 Gist 链接发到公开场合，也不要把证件号、住址等敏感信息写进 Gist 简历。

## 7. 安全

- **传输**：对招聘网站、GitHub 与你选的云端 AI 平台的请求全部走 HTTPS；唯一例外是你自己填的本地或自建端点（如 `http://localhost:11434`），那是你与你自己端点之间的通信。
- **存储**：依赖浏览器提供的扩展存储隔离 —— 网页与扩展之间、扩展与扩展之间互相隔离；但**本地存储本身不加密**。
- **风险面**：由于我们没有服务器，不存在"服务端数据泄露"这一类风险；实际风险只有两处 —— ① 你本机的浏览器配置目录被他人读取；② 你选择的 AI 平台如何处理你发过去的内容。
- **降低风险的建议**：
  1. 用设置了额度上限的 API Key，并定期轮换。
  2. 投递前对简历脱敏（手机号、身份证、住址、前雇主敏感项目名）。
  3. 敏感度高的求职场景改用本地模型端点（如 Ollama），让简历不出本机。
  4. 不要在共用电脑的浏览器配置文件里保存长期有效的 Key。
